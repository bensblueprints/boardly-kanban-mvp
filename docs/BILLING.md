# Boardly accounts, members, company chat and AI funding

Company members inherit every project in that company. Direct project members see only that project. Editors manage tasks/files and use company-owner AI funding; viewers read and download. Both can participate in company team chat when they hold company-wide membership. The account owner manages structure and company mail and can optionally delegate selected connection and member controls. Added users sign in with Clerk email codes using the link in Members; Boardly does not automatically email an invitation. A distinct Clerk user counts once per sponsoring account, including pending users and the owner.

Shared companies appear on the Companies screen even while a member is in their personal account. Selecting a shared company opens the correct sponsoring workspace. Membership discovery and the company tree refresh every three seconds while the page is visible, and on focus; the selected workspace is remembered per signed-in user in the browser tab. Company grants expose all projects in that company; a direct project grant exposes its parent company for navigation with only the permitted projects. Revocation removes the shared company and clears routes when the selected workspace is no longer available.

Company → Members → Permission scopes lets the sponsoring owner enable SSH, GitHub, Environment, Payment connections and Members independently for each grant. All five default off, including existing memberships. The company panel also lists project-only members, whose scopes stay limited to that project. Company scopes inherit to its projects; direct project scopes require owner review after a move to another company. Only the sponsoring owner can edit extra scopes; changes are audited in memberships.db.

SSH and GitHub scopes permit managing connections and using enabled connections from the member's Work runs. The member still needs the task Editor role for Work, which uses the company owner’s funding. Scope checks run before tools are advertised, before calls and during provider operations. Environment scope permits setting and deleting variables but never reveals saved values. Payment connections permits managing cards and billing addresses, while spending limits, agent purchase authorization and purchase reconciliation stay with the owner. Members scope permits adding/removing ordinary members and changing task roles within the delegate's own access; it cannot change their own grant, members with extra scopes, or assign a task role higher than their own. It cannot delegate extra scopes.

Basic Free includes 1 company, 1 user and 2 GiB; Serial Entrepreneur is $79/month for 3 companies, 5 users and 10 GiB; Agency is $299/month for 100 companies, 300 users and 1 TiB. Additional licensed users cost $9/month on every plan. Ben's configured owner ID has unlimited companies/users/storage. Seats are purchased explicitly in hosted checkout; adding a member never silently purchases a seat. Removing a member frees its seat; reduce the paid quantity through billing to stop future seat charges. Over-limit accounts retain existing data and access but cannot add further companies/users/storage.

Company AI work is funded by the workspace owner, including direct project members. The initiating member remains requested_by for permissions; billing_owner_id identifies the sponsor. Personal AI settings configure funding for companies you own, independently of the currently selected shared account. API keys are encrypted with the root project encryption key and bound to the verified Clerk subject. BYOK calls are billed directly by OpenAI; Boardly charges zero. Card-funded calls use Boardly's platform key and meter **2 × actual standard OpenAI token cost**, including cached input/cache writes/output. The rate version and original usage are retained for audit. Prices must be reviewed when the model/provider changes. No paid web/image/audio tools are enabled.

API chat runs a project-scoped Responses API tool loop for tasks and text files. It has no shell, browser, project credentials, mailboxes or project purchase cards. Each tool rechecks project access. The owner can continue using the existing connected Codex execution worker. When the configured owner uses subscription funding, member jobs stay in the scoped server runner: a separate subscription_requests queue asks the owner worker for text/structured tool suggestions only. That ephemeral generation process disables shell, MCP, apps, plugins, browser, hooks and host instructions and receives no project secrets. It never receives a native Work job or project directory. Boardly then rechecks the member’s live permissions before every suggested action. Revocation/cancellation stops generation and rejects later results. The durable queue records payer, initiating member, job, model and reported token usage, clearing transient payload/results after consumption. It does not invent a dollar charge for subscription tokens. API-funded usage is recorded against the owner in personal-ai.db; members pay zero for company work. Worker/server restarts interrupt an unconfirmed model request, and the saved assignment can be resumed. Activity records show actions and public progress, never private reasoning. Opaque model continuity exists only in memory during a run.

## Company team chat

Company → Team chat and the Company team chat panel inside each task open the same company-wide history. Messages persist in the owner workspace’s company_messages table and include a verified sender, timestamp and optional task reference. Viewer members can participate without editing tasks. Posting from a task shares the message with the whole company; the UI states this explicitly. Direct project guests do not automatically receive company-wide chat access: add a company membership when that broader access is intended. API checks happen on every read/write. Moving/deleting a task removes its reference from the old company’s history without erasing the conversation. Messages refresh every two seconds while visible and on focus; earlier history is paginated, and client message IDs prevent duplicate retries.

## Private server setup

Production starts with card billing unavailable. No real card charge or platform API request is possible without the following setup. Keep `BOARDLY_OWNER_ONLY=true` for the existing owner-and-invited-member launch; public signup is a separate launch decision.

1. Add `STRIPE_SECRET_KEY` and `BOARDLY_OPENAI_API_KEY` to `/opt/boardly-clerk/cloud.env` (mode 0600). Use a dedicated OpenAI platform project key. Personal Codex/ChatGPT login is not an API billing key. Never paste either key in project chat, source control or Boardly cards.
2. Preview: `node scripts/setup-billing.cjs --env-file /opt/boardly-clerk/cloud.env`. This makes no network calls and prints no secrets.
3. Apply in Stripe test mode: append `--apply`. This creates monthly plan prices, $9 user quantities, a monthly AI meter, billing portal and signed webhook. It writes generated IDs and the signing secret into the private env file. Preserve that file and the root encryption key in the private backup. Re-running an already configured setup is unnecessary; Stripe idempotency keys have limited retention.
4. Restart only the `boardly-clerk` compose service. Verify test-mode checkout, portal updates, cancellation, failed payments and invoice usage. API usage events contain billionths of USD; the price is `0.0000001` cents per unit. Aggregate monthly rounding happens at the payment provider, not per request. Base plan, additional users and AI usage use separate subscriptions so each can be managed through hosted confirmation.
5. Repeat setup with the production Stripe account/live key only after test-mode invoice verification. The generated portal configuration ID is used explicitly for Boardly sessions. Review the catalog against [OpenAI pricing](https://developers.openai.com/api/docs/pricing) before live usage.

`STRIPE_PORTAL_CONFIGURATION_ID`, `STRIPE_SERIAL_PRICE_ID`, `STRIPE_AGENCY_PRICE_ID`, `STRIPE_SEAT_PRICE_ID`, `STRIPE_AI_PRICE_ID`, `STRIPE_AI_METER_EVENT` and `STRIPE_WEBHOOK_SECRET` are required along with the Stripe secret. The application retrieves authoritative subscriptions; an unsigned webhook, fabricated checkout redirect or client-supplied plan cannot grant allowances. Card-funded AI pauses when its subscription is inactive. Customers confirm the 2× price in Boardly and Stripe before activating billing.

## Usage recovery

Root `personal-ai.db` contains encrypted settings, request holds, original usage and a durable meter-event outbox. It is separate from project exports/sync. Back it up together with `memberships.db`, all workspaces/uploads and `project-secrets.key`. Never restore only a tenant DB after membership or billing changes.

The monthly user cap resets on the first UTC day of each calendar month; the Stripe billing period follows the subscription start date. Before a card-funded API call the server reserves a conservative maximum. On confirmed usage it releases the hold and records the exact cost. No automatic retry is made after ambiguous network failure, process interruption or unknown pricing. Those requests remain `review`; card-funded use pauses until an operator reconciles them against OpenAI's request/cost records. Uncertain usage is not guessed or automatically charged. The request ID is sent as `X-Client-Request-Id`; received response ID/usage are preserved without message content. On review, record the verified provider outcome and adjust the request/ledger in one audited transaction. Do not simply clear unresolved holds.

Pending usage events retry every 30 seconds with stable response identifiers. A failed event remains unreported in the ledger. Monitor `ai_usage WHERE mode='card' AND reported_at IS NULL`; alert and reconcile before Stripe's event acceptance window expires. Application/database outages may delay invoices. Live payment/invoice verification is required before claiming billing is active.
